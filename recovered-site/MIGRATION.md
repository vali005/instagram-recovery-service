# Инструкция переноса и публикации сайта Recovery

Документ описывает безопасный перенос проекта `recovered-site/` на хостинг
и проверку перед публикацией. Он не меняет настройки Netlify, домен, DNS,
права доступа, секреты и публикацию — всё это выполняется только отдельно
с явного разрешения владельца.

## 1. Важное замечание про текущий Netlify preview

Текущий Netlify preview ошибочно собирает **старый проект из корня
репозитория**. Корень репозитория — это прежний сайт, который не является
каноническим источником.

Канонический источник — **только каталог `recovered-site/`**. Любая сборка,
превью или публикация должны использовать его как корень проекта (в терминах
Netlify: Base directory / корень сборки = `recovered-site`). Пока настройка
не исправлена владельцем, результаты preview в корне репозитория не отражают
состояние этого проекта и не должны использоваться для приёмки.

## 2. Требования к окружению

- Node.js `>=22.13.0` (проверяется полем `engines` в `package.json`)
- npm 10+ (использовался npm 11)
- Linux: скрипты установки и сборки используют `flock`, `curl` и GNU `timeout`

## 3. Команды

Все команды выполняются из каталога `recovered-site/`:

```bash
npm ci             # установка строго по package-lock.json
npm run lint       # ESLint по исходникам
npm test           # сборка + все тесты (rendered-html, request-flow, accessibility, seo-audit)
npm run build      # production-сборка через scripts/build-verified.sh
```

## 4. Каталоги сборки

- Корень сборки: каталог `recovered-site/`.
- Результат production-сборки: каталог `recovered-site/dist/`
  - `dist/client/` — статические ассеты клиента (включая `favicon.svg`,
    `og-image.svg`, собранные CSS/JS);
  - `dist/server/` — серверный бандл приложения (`index.js`).
- Служебные каталоги `.sites-runtime/`, `node_modules/` — временные,
  в Git не попадают.

Публиковать нужно артефакты сборки из `recovered-site/dist/`; источником
сборки всегда должен быть сам каталог `recovered-site/`.

## 5. Публичные переменные окружения

Допустимы только перечисленные ниже переменные. Все они необязательные и
задают публичные контактные ссылки; реальные значения в репозиторий и в этот
документ не включаются:

| Переменная | Назначение | Пример заполнителя |
| --- | --- | --- |
| `NEXT_PUBLIC_RECOVERY_PHONE_HREF` | ссылка звонка/мессенджера для блока «Телефон» | `tel:+0000000000` |
| `NEXT_PUBLIC_RECOVERY_PHONE_LABEL` | подпись телефона на странице | `+0 000 000-00-00` |
| `NEXT_PUBLIC_RECOVERY_EMAIL_HREF` | ссылка почтового контакта | `mailto:example@example.com` |
| `NEXT_PUBLIC_RECOVERY_EMAIL` | публичный email для Schema.org | `example@example.com` |
| `NEXT_PUBLIC_RECOVERY_PHONE` | публичный телефон для Schema.org | `+0 000 000-00-00` |

Шаблон значений — файл `recovered-site/.env.example`. Переменные без значений
безопасны: контакты просто не отображаются и не попадают в Schema.org.

Никакие секреты, ключи, токены, пароли, SMS-коды, резервные коды, документы
или платёжные данные не должны задаваться через эти переменные или попадать
в код: форма заявки их не собирает, а автоматическая внешняя отправка данных
отсутствует по дизайну.

## 6. Безопасная проверка превью

1. Локальная проверка перед переносом:
   ```bash
   npm run build
   npm run start     # поднимает собранное приложение
   ```
2. Проверить все маршруты на ответ 200:
   `/`, `/account-blocked`, `/account-hacked`, `/no-phone-email-access`,
   `/login-code-not-arriving`, `/account-protection-guide`,
   `/knowledge-base`, `/privacy-policy`; также `/sitemap.xml` и `/robots.txt`.
3. Проверить metadata каждой страницы: уникальные `title`/`description`,
   canonical на собственный адрес, Open Graph и Twitter-теги, favicon.
4. Проверить форму заявки: согласие обязательно, кнопка отправки отключена
   без согласия, обращение только формируется локально для пользователя,
   внешняя отправка не выполняется.
5. Убедиться, что несуществующие маршруты отвечают 404.
6. Автоматические проверки покрываются тестами: `npm test` должен быть зелёным.

## 7. Откат

- Публикация выполняется из конкретного коммита ветки; откат — повторная
  публикация предыдущего рабочего коммита (или предыдущего артефакта `dist/`).
- Перед публикацией зафиксируйте, какой коммит и какая сборка уходят на хостинг.
- Изменения домена, DNS и настроек публикации при откате не трогаются.

## 8. Что остаётся за пределами этой инструкции

Домены, DNS, платежи, GitHub Actions, права доступа, секреты хостинга и
конфигурация публикации (включая исправление настройки Netlify) меняются
только отдельной задачей с явного подтверждения владельца.
